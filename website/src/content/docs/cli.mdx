## Dashboard

```sh
burnlist [--port <port>] [--scan-root <repo[,repo...]>]
```

Launches the loopback observer dashboard.

## Plan protocol

```sh
burnlist --plan <burnlist.md> --check
burnlist --plan <burnlist.md> --digest
burnlist --close-completed [--scan-root <repo[,repo...]>]
burnlist --stamp
```

`--check` validates the active queue and completed ledger. `--digest` prints a completion digest once the active queue is empty. `--close-completed` adds a digest when needed and moves empty in-progress Burnlists to completed. `--stamp` prints a local ISO timestamp for completion records.

## Lifecycle

These commands act on the current repository by default, or on an explicit `--repo <path>` target. The lifecycle order is `new` → `ready` → `start` → `burn` → `close`.

| Command | Description |
| --- | --- |
| `burnlist new [--repo <path>]` | Create a new Burnlist. |
| `burnlist show <id>[#<item>] [--repo <path>]` | Show a Burnlist or one of its items. |
| `burnlist ready <id> [--repo <path>]` | Move a Burnlist to ready. |
| `burnlist start <id> [--repo <path>]` | Move a ready Burnlist into progress. |
| `burnlist burn <id> <item> [--check] [--repo <path>]` | Complete a Burnlist item; `--check` validates it. |
| `burnlist close <id> [--repo <path>]` | Close a completed Burnlist. |

Lifecycle commands print the next useful command and the canonical local
dashboard URL when one is available. `show <id>#<item>` also prints the stable
item deep link.

## Operational recommendation

```sh
burnlist recommend <id>#<item> [--json] [--repo <path>]
```

`recommend` reads one item from the Active Checklist and deterministically
suggests the lightest fitting control. It reports direct work or a `gate`,
`review`, or `branch` Loop; a provider-neutral model class and effort; P0–P4
review handling; a task-fit metric or Oven signal; a coarse-to-fine sequence;
and observable costs worth optimizing.

The result is advisory: the user may accept, change, or ignore it. Burnlist
does not select, install, authenticate, or launch a model provider. Human
output ends with an actionable `Next:` command plus the canonical
`Dashboard:` URL. `--json` emits
`burnlist-operational-recommendation@1` for tooling.

## Loops

```sh
burnlist loop assign <ItemRef> <LoopRef> [--repo <path>]
burnlist loop unassign <ItemRef> [--repo <path>]
burnlist loop view <LoopRef|ItemRef|review> [--repo <path>]
burnlist loop create <ItemRef> [--repo <path>]
burnlist loop next <RunRef> [--repo <path>]
burnlist loop submit <RunRef> (--outcome <complete|approve|reject|escalate> | --result <file>) [--repo <path>]
burnlist loop claim <RunRef> [--repo <path>] # recovery/diagnostics
burnlist loop report <ClaimRef> (--outcome <complete|approve> | --result <file>) [--repo <path>]
burnlist loop abandon <ClaimRef> --reason <host-cancelled|host-lost|expired> [--repo <path>]
burnlist loop pause|stop <RunRef> [--repo <path>] # idle Run only
burnlist loop complete <RunRef> [--repo <path>]
burnlist loop list [--repo <path>]
burnlist loop status|inspect <RunRef> [--repo <path>]
burnlist loop reconcile <RunRef> --recovery-proof <hex> [--repo <path>]
burnlist loop capability inspect <id> [--repo <path>]
burnlist loop capability trust <id> --revision cp1-sha256:<hex> --grants <json-file> [--repo <path>]
burnlist loop setup status [--repo <path>]
```

An item either runs directly with no assignment or uses one of exactly three
built-ins: `loop:builtin:review`, `loop:builtin:gate`, or
`loop:builtin:branch`. Branch fan-out is orchestrated by the current host;
Burnlist does not schedule branch workers. Agent providers are invoked by the
host, never by Burnlist. In the normal flow, `next` returns a small prepared
host task and `submit` returns its semantic outcome by RunRef; Burnlist then
advances trusted checks and gates. `claim`, `report`, `abandon`, and
`reconcile` expose lower-level recovery and diagnostics. Only `loop complete`
applies a converged Run to the Burnlist. See [Loops](/loops).

## Registry

```sh
burnlist register [path]
burnlist unregister [path]
burnlist roots [--prune]
burnlist init [path] [--track]
```

`init` scaffolds `notes/burnlists/{draft,ready,inprogress,completed}/` and registers the root. `register` adds an existing repository. `roots` lists registered roots with health, while `--prune` drops missing ones. `unregister` removes a registered path.

## Ovens

```sh
burnlist oven <list|view|use|set|bind|unbind|bindings|event|adopt|upgrade|create|update|fork> ...
```

Author and inspect Ovens. Ovens carry an `id@version` identity and can be vendored and pinned per project with `adopt` (committed under `.burnlist/ovens/<id>/`) and opt-in `upgrade`.

```sh
burnlist oven use <id> [--repo <path>] [--force]
burnlist oven set <id> <path|-|json> [--repo <path>]
```

`use` adopts a shipped Oven. It validates and binds only an existing shipped
`example/data.json`; without that exact file it adopts only, creates no data or
binding, and prints the `oven set` next step. `set` accepts a file, stdin, or
inline JSON. It validates first with the built-in handler's producer-input
validator, then atomically writes `.local/burnlist/data/<id>.json` and its
binding. A custom Oven without a runtime validator checks all declared source
pointers and prints a `shape-only` warning: pointer presence does not prove
types, freshness, provenance, or truth. Rejection writes nothing on a fresh
install and preserves the exact prior data and binding on an existing one.
JSON Schema is informational documentation, never `set` authority or package
identity. See [Create your own Oven](/ovens/authoring).

## Skills

```sh
burnlist install [--global] [--agent codex,claude] [--commit] [--force] [--dry-run]
burnlist uninstall [--global] [--agent codex,claude] [--dry-run] [--purge]
```

Registers (or removes) the bundled Burnlist skill for Claude Code and/or Codex, per-repository by default or globally with `--global`. Independent of Hooks below — install one, the other, or both. See [Install](/install).

## Hooks

```sh
burnlist hooks <install|uninstall|status> [--agent codex,claude] [--untracked]
```

Independent of Skills above. See [Install](/install).
Hooks publish bounded observations only; they cannot advance a Loop or change
canonical item state.

## Options

| Option | Description |
| --- | --- |
| `--auto-port` | Try the next available loopback port. |
| `--host <host>` | Bind host; loopback is required by default. |
| `--state-dir <path>` | Override ignored dashboard observer state. |
| `--ovens-dir <path>` | Override launch-repository custom Oven storage only. |
| `--runs-dir <path>` | Override Run snapshot storage. |
| `--oven-data <id=path>` | Bind one Oven to a read-only normalized JSON payload. |
| `--version`, `-v` | Print the version. |
| `--help`, `-h` | Print help. |
