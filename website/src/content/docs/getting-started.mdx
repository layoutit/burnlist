Burnlist is a repo-local burndown tracker with a read-only observer dashboard and declarative **Ovens**. It stores work in a shrinking Markdown checklist and renders live progress; it owns task state, not implementation, tests, or delivery. It is built for planning and observing an agent's work — but it never executes your work or drives your agents.

Burnlist has zero runtime dependencies: it uses pure Node built-ins and ES modules, and runs on Node.js 18 or newer.

## The three concepts

- **Burnlist** — your list of work. Items complete atomically on evidence and leave the active list only once truly done; the list burns down to zero. It answers "what do I do next, and is it really done?"
- **Oven** — a read-only dashboard view that renders honest signals over your own data (progress, metrics, diffs) so you see truth, not vibes. It answers "how are we actually doing?"
- **Lane** — a split of one large Burnlist into parallel sub-lists so independent tracks burn down side by side. Reach for it when a plan has genuinely independent work streams.

To design an Oven that measures honest evidence, see [Designing Ovens](/ovens/designing-ovens).

## Soft orchestration, end to end first

Burnlist coordinates task state, optional [Loops](/loops), proof, and
observation without taking over the project. The repository still owns its
architecture, implementation strategy, tests, domain tools, deployment, and
proof authority.

Unless the repository or user chose another order, work coarse to fine:

1. Establish the thinnest path that reaches the real end-to-end outcome.
2. Prove that path with the declared repository check and, when useful, a
   user-approved Oven signal.
3. Refine internal layers, edge cases, performance, and polish without
   replacing the working vertical slice.

This is a default execution shape, not a command to restructure the project.

## Explore the CLI

Install the CLI, initialize the repository, then create a burnlist. Use the built-in help to see every available command.

```sh
npm install --global burnlist
burnlist init
burnlist --help
burnlist new
```

For an item still in the Active Checklist,
`burnlist recommend <id>#<item>` prints an optional control profile and the
next command; see the
[CLI reference](/cli#operational-recommendation).

The core workflow moves a burnlist item through its lifecycle:

`new` → `ready` → `start` → `burn` → `close`

Useful commands include `burnlist show <id>`, `burnlist ready <id>`, `burnlist start <id>`, `burnlist burn <id> <item>`, and `burnlist close <id>`. Run `burnlist --help` for the full list.

You can also launch the dashboard server with `burnlist`, create a workspace with `burnlist init`, manage registered roots with `burnlist register`, `burnlist unregister`, and `burnlist roots`, and manage hooks with `burnlist hooks <install|uninstall|status>`.
